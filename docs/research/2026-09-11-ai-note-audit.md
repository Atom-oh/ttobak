# AI 노트·MCP 기능 점검 — 2026-09-11

## 판단과 범위

기준 커밋은 `f935290`이다. 녹음, 화자 분리, 요약, 문서 편집, 계정 공유,
MCP 도구는 이미 갖추고 있지만, **저장한 내용과 AI가 실제로 읽는 내용 사이의
불일치 때문에 신뢰할 수 있는 AI 노트라고 단정하기 어려웠다.**
기능 개수가 아니라 입력 보존, 수정 반영, 접근 권한, 오류의 가시성을 기준으로
코드를 추적하고 합성 데이터로 재현했다.

수정은 PR #188(MCP), #189(요약·원문), #190(Q&A), #191(S3 경로 검증 선행
배포), 그리고 이 기록을 포함한 검색 최신화 변경으로 나누었다.
아래 표는 이 변경들 전체의 범위를 다룬다.

이 점검은 실제 고객 녹음에 대한 전사 정확도·요약 품질 평가가 아니다.
아래 테스트 통과는 데이터 전달과 오류 처리가 맞다는 증거이며,
모델이 항상 정확한 결론이나 액션 아이템을 만든다는 증거는 아니다.

## 재현한 문제와 수정

| 문제 | 수정 및 회귀 검증 |
| --- | --- |
| 전사 B를 선택해도 A의 화자별 텍스트가 요약 입력을 대체함 | 선택한 전사본을 유지하고, B에는 A의 근거 링크를 붙이지 않는다. 실제 모델 요청을 캡처하는 Go 테스트로 입력과 저장 결과를 검증한다. |
| A를 수정해도 이전 세그먼트가 남아 정정 전 내용이 다시 사용됨 | 변경된 A와 세그먼트 무효화를 같은 부분 쓰기로 저장한다. 이전 데이터도 전체 텍스트가 일치하는 세그먼트만 사용한다. |
| 사용자가 직접 작성한 메모가 요약·회의 Q&A 입력에서 누락됨 | 메모를 별도 출처로 포함한다. 메모만의 정보를 회의 발언·합의로 단정하거나 녹취 링크를 꾸미지 않도록 구분한다. |
| 토큰 제한으로 잘린 모델 응답도 완료된 요약으로 저장 가능 | 완료 이유, 텍스트 블록, 빈 응답을 검사하고 불완전한 응답은 성공 저장 전에 거부한다. |
| MCP에서 개인 노트의 저장·조회·수정이 연결되지 않음 | 기존 인증된 개인 문서 API를 연결한다. 수정은 기존 ID를 유지하며, 명시한 Account만 공유 공간으로 사용한다. |
| MCP의 계정 필터·계층 정보 연결이 앱보다 뒤처짐 | `accountIds` 필터와 `parentAccountId`를 노출한다. 그룹 조회는 접근 가능한 하위 ID를 명시적으로 포함한다. 계층으로 권한을 상속하지 않는다. |
| 오류 상태의 JSON 응답을 MCP가 성공으로 반환 가능 | HTTP 성공 여부를 먼저 검사하고 도구 오류로 전달한다. |
| 한글·이모지가 네트워크 청크 경계에서 손상될 수 있음 | UTF-8 스트림 디코딩을 사용하고 바이트 단위로 분할한 응답을 그대로 복원하는 테스트로 검증한다. |
| 원문 저장에 실패해도 편집창이 닫히고 성공 시 화면도 오래된 값을 표시함 | 실패하면 초안과 편집창을 보존하고 오류를 표시한다. 성공한 값만 화면에 반영하며 저장 중 중복 조작을 막는다. |
| 계정 멤버 권한으로 볼 수 있는 회의가 Q&A에서 누락됨 | 직접 공유와 계정에 공개된 회의를 합치고, 현재 회의 상태와 정확한 계정의 멤버십을 다시 검증한다. |
| 긴 전사를 저장한 S3 객체를 Q&A 역할이 읽지 못함 | 정확한 버킷·인가된 미팅 ID·전사 필드를 검증하는 코드를 먼저 배포한 뒤 `transcripts/*`의 `GetObject`만 부여한다. 편집 가능한 본문은 S3 읽기 지시로 취급하지 않는다. |
| 편집 후 KB의 예전 발췌문이나 캐시가 계속 답변에 사용됨 | 검색 후보와 현재 본문을 분리한다. 캐시가 적중해도 현재 권한과 저장된 메모·요약을 다시 읽으며, 삭제·권한 회수된 결과는 제외한다. 검색 서비스 실패는 빈 성공이 아닌 오류로 전달한다. |

관련 구현: `backend/internal/service/bedrock.go`, `meeting.go`,
`backend/python/qa/{handler,tools,prompts}.py`, `mcp-server/src/{api,index}.ts`,
`frontend/src/components/meeting/TranscriptSection.tsx`.

## 남는 중요한 한계

1. **KB 검색 후보의 수정 반영은 아직 부족하다.** 완료된 요약을 내보낸 뒤
   `UpdateMeeting`으로 저장한 변경은 KB S3 문서를 다시 만들지 않는다.
   `SyncKB`도 기존 객체의 색인만 시작한다. 이번 변경으로 **검색에 잡힌 회의의
   본문은 현재 저장본**을 사용하지만, 새 용어가 생긴 회의가 검색 후보에 들어오지
   못하는 문제까지 해결되지는 않는다.
   이를 해결하려면 저장 버전이 있는 내보내기 작업, 재시도 가능한 처리,
   색인 중/실패 상태, 캐시 무효화를 함께 구현해야 한다.
   “수정한 납기 24일”이 이전 “20일”을 대체하는지, 저장이 역순 완료되어도
   오래된 버전이 최신 색인을 덮어쓰지 않는지를 검증해야 한다.
2. **개인·계정 문서함의 Markdown은 자동 RAG 색인 대상이 아니다.**
   이번 MCP 연결은 저장된 문서를 직접 읽고 편집하는 경로다.
   문서함과 KB 업로드를 동일한 검색 범위로 설명해서는 안 된다.
3. **회의 첨부 문서의 내용 추출이 빠져 있다.** PDF/PPTX/DOCX/MD 파일은
   이미지 분석과 달리 본문이 요약에 들어가지 않고 파일명·링크만 남는다.
   기존에 알려진 제한이며 이번 점검에서 새로 발견한 결함으로 세지 않았다.
4. **긴 회의와 의미 정확도에 대한 평가가 필요하다.**
   MCP 전체 회의 조회는 큰 전사 데이터를 반환할 수 있다. 구간별 조회와
   출처 위치가 있는 검색 결과가 필요하다. 요약 평가는 합의/제안 구분,
   부정 표현, 수치 정정, 담당자·기한 미확정, 여러 오디오 파트, 메모와 발언의
   충돌을 포함한 검토된 합성 자료부터 마련하는 것이 적절하다.

## 검증 방법

- MCP: 실제 stdio 서버에 연결해 개인 노트 생성→목록→읽기→수정,
  명시적 공유 범위, 오류, 계정 필터를 검증한다. HTTP 요청만 대역으로
  교체하며 실제 자격 증명이나 사용자 데이터를 읽지 않는다.
- 요약: DynamoDB·Bedrock HTTP 경계를 대체해 실제 프롬프트 생성,
  소스 선택, 세그먼트 무효화, 성공 저장 여부를 확인한다.
- Q&A: 공유 후 합류, 탈퇴, 공개 해제, 비공개 연결, 페이지 경계,
  긴 전사와 메모를 조합한 회귀 테스트를 사용한다.
- 프런트엔드: 변경 파일 lint와 정적 빌드를 사용한다. 실제 브라우저 조작이나
  실제 Bedrock 응답의 의미 정확도를 검증한 것으로 보고하지 않는다.
  전체 lint에는 기존 오류 15개가 남아 있으므로 전체 lint가 통과했다고
  보고하지 않는다.
