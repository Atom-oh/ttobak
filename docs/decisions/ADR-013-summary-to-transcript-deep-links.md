# English

## Status
Proposed

## Context
When reviewing a meeting summary, users often want to verify or revisit the original conversation that a summary point refers to. Currently, the AI summary (generated by Bedrock Claude) produces markdown text with no connection to the underlying transcript segments. Users must manually scroll through the full transcript to find the relevant portion -- a tedious process for long meetings.

Notion's meeting notes solve this by linking each summary item to the specific conversation segment it was derived from. Clicking a summary bullet scrolls the user directly to that part of the transcript, providing instant context.

Ttobak already has the building blocks: `TranscriptSegment` objects carry `id`, `startTime`, `endTime`, and `timestamp` fields. The frontend renders both a summary section (`AISummaryCard`) and a transcript section (`TranscriptSection`) on the same page. What is missing is the linkage between them.

## Options Considered

### Option 1: Bedrock prompt-based anchor injection
Have Bedrock Claude emit markdown links (e.g., `[summary point](#ts-00:05:32)`) referencing transcript timestamps during summary generation. The frontend renders these as anchor links that scroll to the matching transcript segment.

- **Pros**: Single-pass -- links are embedded at generation time. No post-processing needed. Natural markdown output.
- **Cons**: LLM output is non-deterministic; timestamp formats may vary or hallucinate. Requires prompt engineering to match exact transcript segment IDs or timestamps. Hard to validate correctness at generation time.

### Option 2: Post-processing with timestamp range mapping
After Bedrock generates the plain summary, a post-processing step matches each summary bullet to the most relevant transcript segment(s) using text similarity or explicit time ranges. The backend injects `transcript://` protocol links (similar to the existing `attachment://` pattern) that the frontend resolves to scroll targets.

- **Pros**: Decouples summary quality from link accuracy. Can use embedding similarity or keyword overlap for matching. Follows the established `attachment://` protocol pattern. Links can be validated before storage.
- **Cons**: Additional processing step increases summarization latency. Text similarity matching may produce incorrect links for ambiguous content. Requires a new service method.

### Option 3: Hybrid -- Bedrock emits time hints, post-processor resolves
The Bedrock prompt instructs the model to emit approximate time ranges for each summary point (e.g., `[05:30-06:15]`). A post-processing step snaps these to actual transcript segment IDs and injects `transcript://{segmentId}` links.

- **Pros**: Leverages LLM's contextual understanding for rough alignment. Post-processor ensures links point to real segments. Resilient to LLM timestamp imprecision. Follows the `attachment://` protocol pattern already in use.
- **Cons**: Two-phase processing. Prompt must include transcript with timestamps (already does). Slightly more complex than pure prompt-based approach.

## Decision
Option 3 (Hybrid approach) is chosen.

The Bedrock summarization prompt already receives the full transcript with timestamps. Instructing the model to emit approximate time ranges is a natural extension. The post-processing step provides a safety net: it maps imprecise LLM time hints to actual `TranscriptSegment.id` values, ensuring every link targets a real conversation segment.

This follows the same protocol pattern established by `attachment://` for image references (ADR: inline image support, PR #57), keeping the architecture consistent. The frontend already has a transcript section with segment IDs that can serve as scroll targets -- the only new work is adding anchor IDs and a click handler.

## Consequences

### Positive
- Users can instantly navigate from any summary point to the source conversation
- Increases trust in AI summaries by providing verifiable source context
- Consistent with the `attachment://` protocol pattern already in the codebase
- Transcript segments already have unique IDs and timestamps -- no schema changes needed

### Negative
- Summarization latency increases slightly due to the post-processing step
- Bedrock prompt becomes longer (must instruct time hint format)
- Edge case: very short meetings may not benefit from deep links
- Matching accuracy depends on transcript quality and segment granularity

## Implementation Notes
- Backend: Extend `GenerateSummary` in `bedrock.go` to include time-hint instructions in the prompt and add a `resolveTranscriptLinks` post-processor
- Backend: Use `transcript://{segmentId}` protocol (resolved by frontend, same pattern as `attachment://`)
- Frontend: Add `id` attributes to transcript segment DOM elements in `TranscriptSection`
- Frontend: Add `resolveTranscriptUrls` in `MeetingDetailClient.tsx` (parallel to `resolveAttachmentUrls`)
- Frontend: Implement smooth scroll on transcript link click

# 한국어

## 상태
제안됨

## 배경
미팅 요약을 검토할 때 사용자는 특정 요약 항목이 참조하는 원본 대화를 확인하거나 다시 듣고 싶은 경우가 많습니다. 현재 AI 요약(Bedrock Claude 생성)은 기반 트랜스크립트 세그먼트와 연결되지 않은 마크다운 텍스트를 생성합니다. 사용자는 관련 부분을 찾기 위해 전체 트랜스크립트를 수동으로 스크롤해야 하며, 긴 미팅의 경우 매우 번거롭습니다.

노션의 미팅 노트는 각 요약 항목을 해당 대화 세그먼트에 링크하여 이 문제를 해결합니다. 요약 항목을 클릭하면 트랜스크립트의 해당 부분으로 바로 스크롤되어 즉각적인 컨텍스트를 제공합니다.

또박은 이미 기본 구성 요소를 갖추고 있습니다: `TranscriptSegment` 객체에 `id`, `startTime`, `endTime`, `timestamp` 필드가 있고, 프론트엔드는 같은 페이지에서 요약 섹션(`AISummaryCard`)과 트랜스크립트 섹션(`TranscriptSection`)을 모두 렌더링합니다. 부족한 것은 이 둘 사이의 연결입니다.

## 검토한 옵션

### 옵션 1: Bedrock 프롬프트 기반 앵커 삽입
Bedrock Claude가 요약 생성 시 마크다운 링크(예: `[요약 항목](#ts-00:05:32)`)를 트랜스크립트 타임스탬프를 참조하여 출력합니다. 프론트엔드는 이를 앵커 링크로 렌더링하여 해당 트랜스크립트 세그먼트로 스크롤합니다.

- **장점**: 단일 패스 -- 생성 시 링크가 포함됩니다. 후처리가 필요 없습니다. 자연스러운 마크다운 출력입니다.
- **단점**: LLM 출력은 비결정적이어서 타임스탬프 형식이 다르거나 환각이 발생할 수 있습니다. 정확한 트랜스크립트 세그먼트 ID나 타임스탬프와 일치시키기 위한 프롬프트 엔지니어링이 필요합니다. 생성 시점에 정확성 검증이 어렵습니다.

### 옵션 2: 타임스탬프 범위 매핑을 통한 후처리
Bedrock이 일반 요약을 생성한 후, 후처리 단계에서 텍스트 유사도나 명시적 시간 범위를 사용하여 각 요약 항목을 가장 관련 있는 트랜스크립트 세그먼트에 매칭합니다. 백엔드는 기존 `attachment://` 패턴과 유사한 `transcript://` 프로토콜 링크를 삽입하고, 프론트엔드가 스크롤 대상으로 해석합니다.

- **장점**: 요약 품질과 링크 정확도를 분리합니다. 임베딩 유사도나 키워드 겹침을 사용할 수 있습니다. 기존 `attachment://` 프로토콜 패턴을 따릅니다. 저장 전 링크를 검증할 수 있습니다.
- **단점**: 추가 처리 단계로 요약 지연 시간이 증가합니다. 텍스트 유사도 매칭은 모호한 내용에 대해 잘못된 링크를 생성할 수 있습니다. 새로운 서비스 메서드가 필요합니다.

### 옵션 3: 하이브리드 -- Bedrock이 시간 힌트를 출력하고 후처리기가 해석
Bedrock 프롬프트가 모델에게 각 요약 항목에 대한 대략적인 시간 범위(예: `[05:30-06:15]`)를 출력하도록 지시합니다. 후처리 단계에서 이를 실제 트랜스크립트 세그먼트 ID에 스냅하고 `transcript://{segmentId}` 링크를 삽입합니다.

- **장점**: 대략적인 정렬을 위해 LLM의 맥락 이해를 활용합니다. 후처리기가 링크가 실제 세그먼트를 가리키도록 보장합니다. LLM 타임스탬프 부정확성에 대한 복원력이 있습니다. 이미 사용 중인 `attachment://` 프로토콜 패턴을 따릅니다.
- **단점**: 2단계 처리가 필요합니다. 프롬프트에 타임스탬프가 포함된 트랜스크립트를 포함해야 합니다(이미 포함 중). 순수 프롬프트 기반 접근 방식보다 약간 더 복잡합니다.

## 결정
옵션 3(하이브리드 접근 방식)을 선택합니다.

Bedrock 요약 프롬프트는 이미 타임스탬프가 포함된 전체 트랜스크립트를 수신합니다. 모델에게 대략적인 시간 범위를 출력하도록 지시하는 것은 자연스러운 확장입니다. 후처리 단계는 안전장치를 제공합니다: 부정확한 LLM 시간 힌트를 실제 `TranscriptSegment.id` 값에 매핑하여 모든 링크가 실제 대화 세그먼트를 가리키도록 보장합니다.

이는 이미지 참조를 위해 `attachment://`로 확립된 동일한 프로토콜 패턴을 따르며(PR #57의 인라인 이미지 지원), 아키텍처의 일관성을 유지합니다. 프론트엔드의 트랜스크립트 섹션에는 이미 스크롤 대상으로 사용할 수 있는 고유 ID와 타임스탬프가 있는 세그먼트가 있으므로, 새로운 작업은 앵커 ID 추가와 클릭 핸들러뿐입니다.

## 영향

### 긍정적
- 사용자가 모든 요약 항목에서 원본 대화로 즉시 이동할 수 있습니다
- 검증 가능한 소스 컨텍스트를 제공하여 AI 요약에 대한 신뢰도가 향상됩니다
- 코드베이스에 이미 있는 `attachment://` 프로토콜 패턴과 일관성을 유지합니다
- 트랜스크립트 세그먼트에 이미 고유 ID와 타임스탬프가 있으므로 스키마 변경이 필요 없습니다

### 부정적
- 후처리 단계로 인해 요약 지연 시간이 약간 증가합니다
- Bedrock 프롬프트가 길어집니다(시간 힌트 형식 지시 필요)
- 엣지 케이스: 매우 짧은 미팅은 딥 링크의 이점이 적을 수 있습니다
- 매칭 정확도는 트랜스크립트 품질과 세그먼트 세분성에 따라 달라집니다

## 구현 참고사항
- 백엔드: `bedrock.go`의 `GenerateSummary`에 시간 힌트 지시 사항을 프롬프트에 추가하고 `resolveTranscriptLinks` 후처리기를 추가합니다
- 백엔드: `transcript://{segmentId}` 프로토콜을 사용합니다 (프론트엔드에서 해석, `attachment://`와 동일한 패턴)
- 프론트엔드: `TranscriptSection`의 트랜스크립트 세그먼트 DOM 요소에 `id` 속성을 추가합니다
- 프론트엔드: `MeetingDetailClient.tsx`에 `resolveTranscriptUrls`를 추가합니다 (`resolveAttachmentUrls`와 병행)
- 프론트엔드: 트랜스크립트 링크 클릭 시 부드러운 스크롤을 구현합니다
